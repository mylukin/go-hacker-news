## Decker, a platform that builds on the legacy of Hypercard and classic macOS

- 原文链接: [Decker, a platform that builds on the legacy of Hypercard and classic macOS](https://beyondloom.com/decker/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49060856)

Decker is a tool for making interactive documents with images, sound, text links, and code, inspired by old tools like HyperCard and classic MacOS. It works in your browser or as a native app on Windows, Mac, Linux, and BSD.

Decker aims to be easy to use, just like HyperCard, but adds helpful modern features. You get deep undo history, scroll wheel and touchscreen support, better keyboard navigation, and ways to edit many things at once. The look is very simple and a bit old-school, using only black and white pixel art, which helps people focus and be creative without too many choices. You can use Decker to make e-zines, notes, slides, games, or just doodle. Finished projects are saved as HTML files that run anywhere, making sharing easy.

For more complex projects, Decker has its own scripting language called Lil. Lil is inspired by Lua and Q, so it mixes easy-to-learn commands with some smart features, like doing math with lists and using a built-in query system. You can build new widgets and copy them as plain text. Every project is like a toolbox—you can take parts out and use them in something else.

Decker also works well with the command line and comes with a Lil interpreter called Lilt. Lilt can run scripts, change Decker files, and even work without a window. You can use it for scripts on many systems. Decker files are just text, so they work with Git or SVN.

There are no ads, tracking, or annoying pop-ups in Decker. It is free and open-source under the MIT license. The website has many examples, libraries, and guides, plus a community on Itch.io and regular game jams for sharing projects.

In the comments, many people feel nostalgic about HyperCard, saying Decker brings back good memories and makes it easy to start building things again. Some users like that Decker is simple and encourages creativity, especially for beginners or those who want to quickly test ideas. Others mention the Lil scripting language, saying it is both simple and powerful, though a few wish it was more like other popular languages.

A few commenters point out that the black-and-white “ditherpunk” style is charming, while others wonder if it could support more colors. Several people praise the choice to make saved files self-contained HTML, which helps with sharing and long-term storage. Some ask about embedding Decker decks into bigger web projects, and others talk about using it in schools or teaching kids to code.

One user says they like how there is no tracking or ads, and another mentions that the open-source license and text-based files make Decker good for archiving and future-proofing. There are also some who wish there were more ready-made examples, or ask about the learning curve for non-programmers. Overall, the mood is positive, with many excited to try Decker or recommend it to friends.

Overall, most commenters agree: compromise is part of every design, and picking the right tradeoffs is what makes a product good or bad.

## Introduction to Data-Oriented Design [pdf]

- 原文链接: [Introduction to Data-Oriented Design [pdf]](https://www.gamedevs.org/uploads/introduction-to-data-oriented-design.pdf)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49060724)

This article explains Data-Oriented Design (DOD) and how it is different from Object-Oriented Design (OOD), especially for game development. The main idea is to focus on how data moves in memory, instead of how code is organized.

The article says that performance is often limited by how fast the CPU can read and write memory. Reading from memory can be slow, and using objects can make it even slower because data is spread out. In OOD, data for each object is mixed with other data, making it hard for the CPU to read only what it needs. For example, if you have four “Bot” objects, each with position, modifier, and aim direction, reading and updating them means lots of cache misses and slow memory reads.

DOD changes this. Instead of keeping all data mixed in objects, it puts similar data together in simple arrays. So, all positions are in one array, all modifiers in another, and so on. This way, when you need to update all bots, you read from simple arrays, which is much faster for the CPU. The code becomes a loop over the data, reading only what is needed and writing results to a linear array. This approach makes code faster, smaller, and easier to parallelize.

The slides also show examples with cache lines and how DOD keeps memory access simple. DOD also helps when using threads or offloading work to GPUs, because you know exactly what data you need and when. The author says that not everything needs to be an object and that, in games, you often know your data up front, so you can organize it for speed.

In the comments, some people agree that DOD brings big speed improvements, especially for games and real-time tasks. Others say OOD is still useful for organizing big and complex projects, where maintainability is more important than raw speed. A few mention that most developers do not need DOD unless they are hitting performance limits. Some warn that DOD can make code harder to understand for new team members who expect objects.

Others add that DOD works best when you process large amounts of similar data, like in games or simulations. Some share stories of switching from OOD to DOD and seeing their code run much faster. But a few people think that mixing both styles is often the best choice, using objects for high-level logic and DOD for performance-critical parts.

There are also questions about how DOD fits with modern languages, as some languages make it harder to use raw arrays and manual memory management. Some commenters say DOD is becoming more popular with new hardware, like GPUs, that work better with simple, flat data. But, others remind that DOD needs careful thought and is not always the right answer for every problem.

Overall, the comments show there is no one right way—both OOD and DOD can be good, depending on the problem and goals.

## The relay market powering token resellers and fraud

- 原文链接: [The relay market powering token resellers and fraud](https://vectoral.com/blog/token-relay-market)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49058993)

This article explains how a hidden market uses “relay” services to resell AI tokens at very cheap prices, helping people get around official limits and sometimes enabling fraud. The author, a software engineer, learned about this while fighting abuse on their own AI platform and discovered that this problem affects many companies.

Relays act as middlemen between users and official AI services, offering access at huge discounts—sometimes over 97% off. The whole system has four layers: merchants make fake accounts and credit cards, pools manage hundreds of these accounts, relays sell access in a neat package, and end-users (like developers and companies) buy the cheap tokens. Two open-source tools, “one-api” and “new-api,” are often used to run relays. These tools themselves are legal, but problems start when they use stolen or abused tokens.

Fraudsters use several tricks: creating lots of free accounts, charging back money after using the service, funding accounts with prepaid cards, and even using open chatbots as hidden relays. Some attacks focus only on burning through a company’s money, not making profit. The buyers are often developers or companies wanting cheap AI access, or bypassing country restrictions.

This market is now so big that there are websites comparing relay prices, affiliate programs, and even daily lotteries where people can win free $100 API keys. The lottery uses cryptographic methods to prove it’s fair, copying methods from crypto gambling sites. As AI companies add more security checks, the fraud just moves to new places.

To fight this, companies can make accounts harder to create, check for strange payment patterns, watch for weird user activity, and set strict spending limits. But the article says there’s no perfect solution—just ways to make attacks harder and less profitable.

In the comments, many readers are shocked by how organized and mature this market has become. Some say it’s like an arms race: as companies add defenses, attackers find new ways in. Others point out that open-source relay tools are not bad by themselves, but become a problem when used for fraud. A few readers wonder if AI providers are partly to blame for making account creation too easy or not having strong enough checks. Some developers admit they have seen these cheap tokens advertised, and worry that honest users might be hurt by stricter rules.

One commenter shares that similar abuse happens in other online services, like cloud credits or VPNs. Another worries that strong anti-fraud measures could make life harder for real users, especially in countries with strict payment systems. There’s also debate about whether using relay services is always wrong—some people see it as “gray market,” not full-on crime, especially if users just want access, not to commit fraud. Overall, most agree that the cat-and-mouse fight between providers and abusers will keep going, and no simple fix exists.

## How to Write English Prose

- 原文链接: [How to Write English Prose](https://thelampmagazine.com/blog/how-to-write-english-prose)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49060295)

This article talks about how to write good English prose, using many examples from classic writers. The author compares two styles from the 1600s: one is full of rich, complex language (like Sir Thomas Browne), and the other is more clear and simple (like the King James Bible). But, even the simple style is not as plain as people often think. The best English writing, the author says, balances beauty and clarity—sometimes using fancy words and sometimes being direct.

The article explains that English prose became great because the language took words from many places and grew more complex over time. The writer shares examples from famous authors, showing how they mix detailed description, strong images, and careful word choices. The author argues that modern writing is often too plain, because people follow rules that say writing should always be simple and short. He disagrees with many popular writing rules, like “always use the active voice” or “never use long words,” saying these rules make writing boring.

Instead, the author shares his own rules: use the best word, even if it is rare; don’t worry if readers need a dictionary; don’t use a thesaurus; and read widely to learn new words. He says both simple and complex styles are hard to do well, but both are needed. He also says to read your writing out loud to check the flow, and to write for readers who enjoy language, not just for those who want quick information. The author warns against only following advice from books like “The Elements of Style,” which he finds too strict and sometimes wrong. He believes writing should be lively, musical, and able to surprise the reader.

In the comment section, many people agree that modern writing is often too simple and dull. Some say that good writers break the rules when needed, and that reading old books helps you learn better ways to write. A few readers defend simple writing, saying it can be beautiful when done right, and that sometimes too many big words make the meaning unclear. Others point out that most people today do not read long or complex writing, so writers need to be careful not to lose their audience.

Some comments talk about the dangers of “fancy” writing that feels fake or shows off. One person says writing should fit its purpose: business writing should be clear, but stories can be rich and detailed. Another says that learning more words is fun, and writers should not be afraid to use them if they fit. A few mention that English is special because it borrows so many words from other languages, making it colorful.

Several readers dislike “The Elements of Style,” agreeing with the author that it is too limiting. Some share their own writing tips, like reading your work aloud, or trying to learn from the best writers in history. In the end, most agree that, while rules are helpful, good writing is about finding your own voice and making the words feel alive.

## How to Block Some of the Bots

- 原文链接: [How to Block Some of the Bots](https://nochan.net/b/Internet-Crap/20260606-How-To-Block-Some-Of-The-Bots/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49060945)

This article talks about how to block unwanted bots from visiting your website, especially if you are not using a CDN. The author gives many ways to stop simple or old bots, but warns you must test first so you do not block real visitors.

The first method is to block any client not using HTTP/2.0; most bots still use HTTP/1.1, including Googlebot. You can set your server (like NGinx) to reject or redirect these clients. The second method is to block whole data centers by getting lists of bad IP address ranges, checking which networks they belong to, and then adding blackhole routes to your server. This saves CPU compared to firewall rules. The third method uses public blocklists to block IPs from certain countries, proxies, Tor nodes, or known abusers. For each method, the author warns about false positives and says you should check your logs before doing this.

Method four focuses on blocking clients by signals like user-agent, accept-language, sec-fetch-mode, and HTTP referer. Most bots do not try hard to look like browsers, so you can block based on certain keywords or missing headers. There are example NGinx rules to block user-agents with words like "bot," "curl," or "spider." Other methods include using NFTables to block suspicious TCP packets, making ports stateless, and limiting window sizes or MSS values. The author also mentions adding headers to warn bots about adult content, or to stop them from indexing your site. Compressing content with Brotli also stops some bots, as many cannot read this format. Finally, there are tips to make it harder for attackers to scan your site.

In the comments, some people like these strict anti-bot ideas and say they use similar tricks, like blocking IPs or rejecting old protocols. Others warn that blocking HTTP/1.1 will stop Googlebot and hurt your search ranking, which could be bad for business sites. Some say that many advanced bots can easily fake headers or use residential proxies, so these methods only stop the lazy ones, not the serious attackers. A few think blocking whole countries or ISPs might block real users, especially if your audience is global. Some users point out that over-blocking can break things for normal people, like those using VPNs, old browsers, or mobile networks. Others like the use of Brotli but say that some real browsers might have trouble if not set up right. There’s debate about using blackhole routes versus firewall rules; some say blackholes are faster, others prefer the control of firewalls. A few people share stories where simple user-agent blocks stopped big waves of spam, but others say that bots are getting smarter every year. Some commenters ask for easier solutions or tools, saying this all seems hard for small sites. Many agree that no single method can block all bots, but using a few together can cut down the noise.

## Building the Grace Cathedral experience

- 原文链接: [Building the Grace Cathedral experience](https://blog.playcanvas.com/building-the-grace-cathedral-experience/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49008834)

This article talks about how a team created a 3D, interactive web experience of Grace Cathedral in San Francisco using PlayCanvas and new graphics technology. They worked with Vincent Woo, who had already scanned the cathedral as millions of "Gaussian splats," and turned this data into something you can explore in your browser.

The main technology behind the experience is the PlayCanvas Engine, which uses WebGPU when possible for fast graphics, and falls back to WebGL2 if needed. WebGPU is better because it lets the graphics card do more of the hard work, like sorting and drawing the millions of splats needed for the 3D scene. This means smoother performance, especially when the camera moves around the cathedral.

The app streams its data in a special compressed format called SOG, which lets it load different levels of detail as you explore, so it doesn't use too much memory or take too long to start. There are separate models for the inside and outside of the cathedral, and only one loads at a time to save space.

To keep things running smoothly even on slow devices, the app only redraws the screen when something changes, limits the resolution on phones, and hides parts of the scene you can’t see. There’s also a cool "Peek" feature that lets you cut away a wall to look inside the cathedral, using smart computer graphics tricks to make it look good and efficient.

Other fun touches include a hidden animated flag, moving cars, smooth camera controls, and sound effects that change as you move. All these little details help make the virtual cathedral feel more real and fun to explore.

Everything was built using open source tools: PlayCanvas Engine for rendering, SuperSplat for editing the 3D data, and the SOG file format for sharing it. The team encourages others to try making their own 3D splat experiences and offers guides and a Discord community for help.

Commenters on Hacker News were impressed by the smooth performance and quality of the experience, especially how fast it loads and runs even on normal laptops and phones. Some users appreciated that the project is open source and that there are guides for making your own splat apps. Others discussed the technical parts, like how WebGPU is faster than WebGL2, and how streaming only the needed data is smart for big 3D models.

A few developers asked about the challenges of supporting both WebGPU and WebGL2 and how the team handled browser compatibility. Some wondered about the SOG format and if it could help with other projects that use lots of 3D data. There were questions about making the app even lighter for very slow devices, and suggestions for more detailed sound effects or VR support in the future.

One person enjoyed finding the hidden flag and liked the little surprises in the experience. Another mentioned how the cutaway "Peek" feature was both fun and useful for exploring the inside. A few people compared this project to other cathedral or museum scans on the web, saying this was the fastest they had seen.

Finally, several users said this kind of open, explorable 3D experience could be great for education, tourism, or games, and hoped to see more projects like it soon.
