## 350 years ago, this man discovered that light has a finite speed

- 原文链接: [350 years ago, this man discovered that light has a finite speed](https://www.sciencenorway.no/culture-history-history-of-science/350-years-ago-this-man-discovered-that-light-has-a-finite-speed/2737969)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=50536813)

In 1676, Danish scientist Ole Rømer showed that light takes time to travel instead of arriving at once. The article marks 350 years since his discovery, which changed how we understand space.

Rømer studied Io, one of Jupiter’s moons, which regularly passes through the planet’s shadow.
These events happened often enough to work like a clock.
But they appeared to happen later than expected when Earth moved away from Jupiter.
They appeared earlier when Earth moved toward Jupiter.
Rømer explained that light needed more time to reach Earth when the distance was greater.
In September 1676, he predicted that Io would leave Jupiter’s shadow ten minutes later than expected on November 9.
His prediction was right.
He worked out that light needed about 22 minutes to cross from one side of Earth’s path around the Sun to the other.
That suggested a speed of about 225,000 kilometres per second, compared with the true value of about 300,000.
His result was about 25 percent too low, but it showed that light’s speed could be measured.
Earlier thinkers had suggested that light needed time to travel, but Rømer provided evidence.
Some scientists doubted his explanation, while Huygens and later Newton supported it.
About 50 years later, James Bradley found separate evidence through small changes in where stars appeared in the sky.
The discovery also means that looking farther into space lets us see farther into the past.

The project uses a few thousand lines of code. It starts with web addresses and HTTP, the rules browsers use to request pages. Next, you create a window and draw content on the screen. You learn how to fit words onto lines and leave space between them. The browser then reads HTML and builds a tree that shows how the page is organized.

The book explains how to place text and larger blocks on a page. It adds CSS, which controls how page content looks. Links, buttons, and forms let users move between pages and send information to servers. JavaScript support lets a page react to user actions and change its content. Security chapters cover cookies, logins, and attacks that can put user data at risk.

Later chapters explain visual effects and how browsers share work across tasks. They also cover smooth animation, images, and pages placed inside other pages. Other topics include keyboard access, zooming, and reusing earlier results instead of doing the same work again.

## Solid 2.0

- 原文链接: [Solid 2.0](https://www.solidjs.com/blog/solid-2-0-the-long-hold/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=50536387)

The article announces Solid 2.0, a new stable version of the tool for building web pages and apps. It comes five years after Solid 1.0, as more web tools adopt signals and AI changes how people write code.

Signals track changing data so an app knows which parts of the page need updates. Solid now brings work that waits for data into that same system. This means developers can use data from a server without writing as much extra code to manage the wait. The framework also handles problems caused by answers arriving in the wrong order. One example shows a city list updating when someone chooses a different state. Server functions can also send live updates, such as changing stock prices. Another big goal is helping AI tools find and fix their mistakes. During development, Solid can report certain errors with a clear code, a source location, and repair advice. These checks can also help human developers understand why their app behaves badly. Solid removes several older tools because the new system no longer needs them. The team has also retired SolidStart, its extra framework for building full apps. Its key building blocks now live in Solid itself or in separate tools that other projects can use. Before calling this release stable, the team tested 23 release candidates over 14 weeks.

The Hacker News comments were not included, so I cannot report what readers actually said. Instead, there are several useful questions to consider about these changes. For someone starting a new app, fewer tools and less waiting-state code could be a welcome change. For someone with an older Solid app, removing familiar tools raises questions about the work needed to update it. Automatic handling of server requests sounds helpful, especially when users change their choices quickly. But developers will still need to understand what happens when a request is slow or fails. Clear error messages could make AI-written code easier to check, though they cannot prove that an entire app is correct. Developers who do not use AI may value those same checks without caring about the AI focus. Moving shared parts into Solid could help different tools work together, while retiring SolidStart may leave some users wanting a clearer starting point. The real test will be whether these changes make everyday apps easier to build and maintain.
