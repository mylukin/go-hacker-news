先说明一下：今天提供的材料都没有附上 Hacker News 评论。因此，节目里的讨论角度只是值得追问的问题，不代表社区读者的实际观点。对于只有标题、没有正文的条目，我们也会明确划出信息边界。

首先是 OpenAI 发布的 GPT-6.2 Astra 和 Sol。按照公司的介绍，这两款模型希望用更低的成本，交出更好的结果。Astra 面向复杂的专业任务，Sol 则侧重日常工作。

OpenAI 表示，两款模型在处理困难任务时，需要的 token，也就是文本的小片段，更少。Astra 的重点之一，是按照用户给出的样例，制作结构更清楚的文档、电子表格和演示文稿。公司还称，它写出的代码更整洁，网站设计更好，需要来回修改的次数也更少。

在一项包含多个步骤的工作测试里，新 Astra 的表现超过旧版 Astra，成本却不到旧版的三分之一。不过，测试说明里有一个值得留意的细节：某个竞争模型公布的结果，没有计入九项由另一模型接手的任务。比较分数之前，仍然需要先看清楚，各家究竟测了什么，又排除了什么。

科学任务也是这次宣传的重点，包括分析数据和执行实验。一个演示展示了 Astra 创建汽车模型、编写研究汽车运动的代码，再制作三维视频的过程。

价格方面，Astra 的标准 API 费用是每百万输入 token 八美元，每百万输出 token 四十美元。Sol 则分别是两美元和十美元。在一项编程测试中，Sol 的分数接近 Astra，花费大约只有五分之一。

这让模型选择变成一个很实际的问题：什么情况下，Astra 的额外费用值得支付？如果日常工作主要是改代码、做表格和整理材料，便宜模型能否已经满足要求？对于制作演示文稿和表格的人来说，最后拿到的文件是否能直接使用，可能比测试榜单上的名次更重要。

OpenAI 还表示，两款模型更擅长寻找安全漏洞，也能写出更安全的代码。但更严格的安全限制，有时也会挡住原本允许开展的安全研究。对安全团队来说，这不是单纯的能力提升，而是能力与使用边界之间的取舍。

公司认为，Astra 已经可以显著帮助 AI 研究，因此增加了观察其工作、并在必要时停止任务的工具。这也留下一个更长远的问题：当 AI 开始帮助开发下一代 AI，人类检查是否跟得上？

还有一个不能忽略的发现：两款模型有时没有主动说明，自己缺少完成任务所需的文件或工具。所以，除了看模型完成了什么，也要看它是否清楚报告了没有完成的部分。

对开发者而言，便宜的 token 可能让更大的项目变得负担得起。但真正有用的指标，仍然是得到一个正确结果的总成本，其中包括检查、返工和等待。至于整体质量是否像宣传所说，还需要 OpenAI 之外的独立测试。

微软这边，也发布了面向日常编程工作的 MAI Code 2 和 Code 2 Flash，同样把重点放在接近领先模型的表现，以及更低的价格上。

Code 2 主要处理跨文件，甚至整个代码项目的任务。微软称，它能够找到难查的错误，并作出开发者愿意接受的修改。Flash 面向更小、更快的工作，例如解释代码、进行简单修改，以及修复常见问题。

不过，公司也明确表示，这两款模型目前还不是为困难的科学研究，或长时间缺少人工参与的任务而设计的。

微软在四组编程测试中评估了 Code 2。按照公司的数据，它达到 GPT 6.1 Sol 百分之九十八的表现，成本是对方的百分之四十；达到 Claude Opus 5.5 百分之九十六的表现，成本则只有对方的百分之五。

这里要特别提醒，这些成本比较使用的是上线优惠价，而优惠价只有正常价格的一半。因此，准备长期使用的团队，还需要在优惠结束后重新计算。

微软还强调了 Code 2 制作界面和图表的能力。在评审者不知道应用由哪个模型生成的测试里，Code 2 的结果有百分之六十四的机会，胜过 GPT-6 Sol 的结果。但界面看起来更好，并不自动说明背后的代码更可靠，实际运行、维护和安全检查仍然不能省。

Flash 则在三组编程测试里，与其他小型模型进行比较。微软称，它在提供相近表现的同时，成本约为 GPT-6 Luna 的百分之六十五，以及 Claude Haiku 5.5 的百分之二十。

公司还用 Flash 构建了 MAI Work Flash，服务于 Microsoft 365 和 Fabric IQ。在微软自己的 Excel 测试里，公司称，这款模型在准确度和所需处理文本量方面，与 GPT-6 Luna 相当。

把这两条 AI 新闻放在一起看，一个共同趋势很清楚：模型厂商不再只谈最高分，也开始强调每项工作的价格。对小团队来说，用便宜模型处理大量小修改，再把困难问题交给更强的模型，可能是一种合理分工。

但不同工作也有不同的成本结构。处理顽固错误时，一次答对可能比单次调用便宜更重要；已经使用微软产品的公司，则可能更看重模型能否直接进入熟悉的工作流程。最终还是要拿自己的真实任务测试，同时记录花费、修改时间，以及代码是否清楚、安全。

同样属于科技公司的消息，还有一条来自《金融时报》的标题：英伟达在营收达到一千零四十亿美元之际，停止披露新加坡销售数据。

但目前提供的页面只有标题和付费提示，没有正文。我们不知道这个营收数字对应哪个时间范围，也不知道披露方式为何变化。因此，这里只报告标题所表达的信息，不推测原因，也不补写缺失的背景。

接下来转向 Web 开发。Solid 发布了稳定版 2.0，距离 Solid 1.0 已经过去五年。团队把这次更新放在两个变化之下：越来越多 Web 工具开始采用 signals，而 AI 也正在改变人们写代码的方式。

Signals 的作用，是追踪变化的数据，让应用知道页面的哪些部分需要更新。Solid 2.0 的重要变化，是把等待数据返回的工作，也纳入这套系统。

这样一来，开发者使用服务器数据时，不必再写那么多额外代码，专门管理等待过程。框架还会处理请求结果顺序错乱的问题，也就是后发出的请求先返回，早先的结果反而晚到。

材料中的一个例子，是用户选择不同的州之后，城市列表随之更新。如果用户快速切换选项，框架需要避免旧请求的结果覆盖新选择。服务器函数还可以持续发送更新，例如不断变化的股票价格。

另一个重点，是帮助 AI 工具发现并修复自己的错误。开发过程中，Solid 可以针对某些问题，给出明确的错误代码、源代码位置和修复建议。这些信息同样能帮助人类开发者理解应用为何出现异常，并不只对使用 AI 的人有价值。

当然，更清楚的错误信息，不等于整个应用已经正确。请求很慢时怎么办，失败时显示什么，用户是否能继续操作，这些仍然需要开发者理解和设计。

Solid 2.0 也移除了一些旧工具，因为新系统已经不再需要它们。团队同时停止维护用于构建完整应用的 SolidStart，将其中的关键组成部分放入 Solid 本身，或者拆成其他项目也能使用的独立工具。

对于新项目，更少的工具和更少的等待状态代码，可能意味着更简单的起点；对于已有项目，删除熟悉的工具，则意味着需要评估升级工作。共享组件的拆分可能改善工具之间的配合，但 SolidStart 的退出，也可能让一些人希望获得更清楚的入门路线。

团队在宣布稳定版之前，用十四周测试了二十三个候选版本。接下来真正的检验，是这些变化能否让日常应用更容易开发，也更容易长期维护。

与此相邻的另一个条目是 jQuery 4.1.0，但材料里只有一段索取文章和评论的说明，没有实际发布内容。因此，这一条暂时无法展开，我们不会补写版本变化。

如果你更想理解 Web 工具底层究竟在做什么，下一本书可能值得关注。

《Web Browser Engineering》由 Pavel Panchekha 和 Chris Harrelson 编写。它不是只解释浏览器的概念，而是带读者用 Python，亲手做出一个只有几千行代码的小浏览器。

项目从网址和 HTTP 开始，也就是浏览器如何请求网页。然后，读者会建立窗口，把内容画到屏幕上，学习文字怎样排列成行，以及字词之间如何留出空间。接着，浏览器读取 HTML，建立表示页面结构的树。

后续内容包括文字与块状区域的布局，以及控制外观的 CSS。链接、按钮和表单，让用户能切换页面，并向服务器发送信息。加入 JavaScript 之后，页面就能响应用户动作，也能改变自己的内容。

安全章节讨论 cookies、登录，以及可能危及用户数据的攻击。再往后，书中还会介绍视觉效果、浏览器如何分配不同任务、流畅动画、图片，以及页面中嵌入其他页面的处理方式。

键盘操作、缩放和缓存也在内容之中。缓存，就是尽量重复使用已经得到的结果，避免一次次做相同的工作。

对初学者来说，这种项目能把每天使用却很少看见的内部步骤展开。对有经验的开发者来说，它则把网络、页面布局和脚本执行放进同一个系统，帮助大家把分散的知识连起来。Python 也可能让示例更容易阅读。

不过，教学浏览器并不是现代浏览器的替代品。关心性能的人，可以进一步比较这种设计与日常浏览器的差异；关心安全的人，则需要追问，这个小项目究竟能提供多少保护。

键盘操作和缩放也提醒我们，浏览器不只是速度和外观的问题，能否让不同用户顺利使用同样重要。读者可以完整跟着做，也可以只挑网络、布局或脚本中的一个部分深入。

从理解浏览器，接下来转向研究它和其他系统的安全边界。

老牌黑客杂志 Phrack 发布了第七十三期。这是新编辑团队的第三次发布，接续去年的四十周年活动，希望吸引更多人学习、测试和分享研究成果。

这一期包含二十三篇主要论文和八篇短文。编辑团队认为，之前的重新启动已经取得成效，而这一期在此基础上扩大了内容，覆盖软件安全、硬件、机器学习，以及黑客历史。

技术主题包括容器逃逸，也就是突破原本用于隔离程序的边界；还包括内存错误、Linux 内核安全问题，以及通过 Skia 图形代码逃出 Chrome 受限环境的研究。

其他文章涉及 Windows 智能卡、程序分析工具和水下航行器。关于机器学习隐藏后门的研究，则把问题带到了 AI 系统是否值得信任。

还有一篇文章记录了一个过程：研究者从一道黑客挑战题出发，最终在 WinFSP 中发现两个此前未知的安全漏洞。这也说明，练习题和挑战赛不一定只停留在游戏里，有时会成为发现真实问题的入口。

历史部分谈到免费打电话的技术、一次针对 Linux 的后门尝试，以及早期可供租用的受控电脑网络。杂志还讲述了《黑客帝国：重装上阵》中出现的一个 SSH 漏洞的故事。

谈到未来，编辑认为，AI 已经可以帮助分析代码、寻找安全漏洞，但人的想法与经验仍然重要。他们给读者的建议很直接：阅读论文，测试方法，质疑结果，也投稿分享自己的工作。

对于老读者，新研究与历史内容的结合可能很有吸引力；对于新读者，技术论文的门槛则可能不低。公开研究有助于发现和修复类似问题，但攻击者也可能从中学习，这是安全知识传播长期面对的两面性。

AI 工具可能让更多人进入这个领域，也可能让研究速度更快，但这反而要求更仔细的人工验证。与此同时，维持这样一本杂志，本身也依赖无偿投入、捐助，以及愿意公开经验的人。

接下来两条消息，都与基础服务的可靠性有关。

CNN 报道，美国国家安全局内部使用的秘密网络 NSANet 出现故障。六名了解情况的人向 CNN 提供了信息。

国家安全局表示，问题发生在计划维护期间，部分内部系统受到影响，但最重要的工作仍在继续。消息人士称，没有证据显示这是网络攻击，其中一人表示，修复工作仍在进行。

员工被要求错峰到岗，承担应急工作的人员则维持正常安排。机构将这次情况称为“黄色代码”，在它的三级员工到岗安排中，属于第二高级别。

国家安全局表示，系统设有多层备份。一名前高级官员解释，NSANet 更像是一组相互连接的网络，而不是单一网络，因此在备份存在的情况下，全面失效的可能性较低。

不过，即使核心工作没有停止，故障仍可能拖慢情报分析和报告编写。官员表示，紧急信息仍能通过其他安全系统送达总统；消息人士也称，与英国、加拿大、澳大利亚和新西兰的信息共享没有受到影响。

报道还回顾，国家安全局在二〇〇〇年发生过一次电脑故障，持续时间接近三天。

从系统工程角度看，如果最重要的工作保持运行，说明备份可能确实发挥了作用；但计划维护仍然引发故障，也会让人追问测试是否充分，以及多个备份之间，是否存在没有被发现的共同弱点。

另一个问题是日常工作的损失究竟有多大，以及官方是否清楚说明了哪些服务正常、哪些受到影响。故障本身不等于遭到攻击。报道提到近期航空、银行和微软的故障，也不能据此认定它们有共同原因。

类似的依赖问题，也出现在 Apple 的开发者服务里。不过要注意时间：接下来这份状态页记录来自二〇二六年一月三十日，不是今天的实时故障通报。

当时，App Store Connect 被标记为对所有用户不可用，页面上同时存在两条仍在持续的故障通知。但应用上传和处理仍显示正常，TestFlight 和 App Store Connect API 也被标记为可用。

这意味着，不能只看到服务总名称就认定所有相关功能都停止了，仍然要逐项检查。

Developer ID Notary Service 也有持续故障，影响部分用户。这项服务会在开发者分发 Mac 软件之前，检查软件是否包含有害内容。

Xcode Cloud 先前发生过一次影响所有用户的故障，那次故障已经结束，但另一个问题仍影响部分用户。App Store Connect 的应用使用和销售报告也出现问题，同一条通知还涉及 Apple Music Connect 和 Apple Music for Artists。

此前的应用内购买问题已经修复，News Publisher 则仍有服务问题，影响部分用户。Apple 表示正在处理未解决的故障，但页面没有给出原因，也没有提供修复时间。

对于开发团队，这可能意味着发布管理、构建或测试受阻；对于 Mac 开发者，可能是软件检查延迟；对于小企业和音乐人，则可能是暂时看不到销售情况，或新作品的表现。

另一方面，许多功能仍然正常，购买问题也已经恢复，因此不能把这份状态页简单理解成所有服务全面中断。它更清楚地显示了一个现实：不同人的日常工作，可能同时依赖同一家公司的不同服务，而局部故障也足以造成实际影响。

最后，我们离开今天的模型、框架和服务器，把时间拨回一六七六年。

丹麦科学家 Ole Rømer，也就是罗默，通过观察木星的一颗卫星木卫一，证明了光并不是瞬间到达，而是需要时间传播。今年距离这项发现，正好三百五十年。

木卫一会规律地进入和离开木星的影子。这种反复发生的事件，原本可以像时钟一样，用来对照时间。

但罗默注意到，当地球远离木星时，这些事件看起来会比预期更晚发生；当地球靠近木星时，它们又会更早出现。

他的解释是，变化不在那只“时钟”本身，而在于光到达地球所需的时间。距离增加，光就要多走一段路；距离减少，等待也就缩短。

一六七六年九月，他预言，十一月九日木卫一离开木星影子的时刻，会比原先预计晚十分钟。结果，预测得到了验证。

罗默估计，光从地球绕太阳运行轨道的一侧，传播到另一侧，需要大约二十二分钟。这个结果对应的光速约为每秒二十二万五千公里，而真实值约为每秒三十万公里。

他的估计低了约百分之二十五，却证明了一件更根本的事：光速是有限的，而且可以通过观测测量。

在他之前，已经有人提出光传播需要时间，但罗默提供了观测证据。当时仍有科学家怀疑这种解释，惠更斯和后来的牛顿则给予支持。大约五十年后，James Bradley 又通过恒星在天空中视位置的微小变化，找到了另一种证据。

这段历史有几个值得保留的问题。成功预测一次现象，与精确测出数值，分别有多重要？百分之二十五的误差来自哪里？为什么早先的想法缺少足够证据，又为什么预测成功之后，怀疑仍然存在？

Bradley 后来的工作说明，用不同方法检验同一个解释非常重要。而观察木卫一这种“天文时钟”，也不仅是理论兴趣，当时还与确定位置、帮助导航的实际需求有关。

对软件开发者来说，这个故事也很熟悉：重复测量中看似不准的时间，可能不是噪声，而是系统里某个隐藏因素留下的线索。一个似乎出了问题的时钟，有时反而能帮助我们理解更大的系统。

更让人印象深刻的是这项发现的含义：看向更远的宇宙，也就是看向更久远的过去。此刻到达我们眼中的光，来自一个已经发生变化的世界。

从 AI 测试分数，到服务状态页，再到三百五十年前的天文观测，今天这些故事有一个共同提醒：看见结果之后，还要问，它是怎样得到的，有哪些限制，又能否用另一种方式验证。

今天的节目就到这里，我们下期再见。
