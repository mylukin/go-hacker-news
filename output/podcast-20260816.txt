Our first story is a response from an embedded engineer in Trinidad and Tobago to a critical post about RISC-V chips. While there are fair technical complaints about RISC-V’s design, the author says many critics from the US and Europe miss what matters most for people outside these regions. In his country, getting hardware is slow and expensive—shipping cheap chips can cost $60 to $200. For him and his students, the price of a chip is not a small detail. It decides if every student can have their own device, or if they just watch one demo. RISC-V makes a real difference because it is cheap, available, and free from big company licenses.

He explains how RISC-V chips, like the CH32V003 and CH32H417, cover everything from low-cost microcontrollers to more powerful chips that can run Linux. He gives examples of his own projects, like a whistle switch and a web browser on a microcontroller, all done with RISC-V. With less than $100, he got all the parts and tools he needed, while just one ARM debugger can cost $200 or more and is much harder to get.

The author disagrees with critics who say one instruction set can’t serve both small and powerful chips. He says RISC-V uses the same base instruction set for everything, so learning one RISC-V chip helps you use others. With ARM, moving to more advanced chips means learning new things and dealing with company rules and contracts.

He also says RISC-V is more open. With ARM, you need special licenses to get advanced features. With RISC-V, anyone can add features, like a memory management unit, without asking or paying extra. This gives much more freedom to engineers everywhere.

About fragmentation—where chips are different in small ways—he admits it is a problem, but says it’s the price for being flexible and fitting many uses. He thinks this is better than being locked out by expensive licenses and rules. He ends by saying that RISC-V is winning not because it’s perfect, but because it’s cheap, open, and available to people everywhere. This means more people can learn, build, and create products, even in places big companies ignore.

Proofs are just the start; real understanding comes from people talking and testing together. Moving real-world needs into formal rules is hard and mistakes can happen. Separating rules and code is even harder as software changes. The article adds that, while this is true, modern tools make it easier to check and change rules, and humans still need to decide what “correct” means.

The paper also argued that fully automatic checking is impossible. The article replies that AI tools are getting better, so maybe this will change. Another worry was that “black box” verification won’t help programmers learn. The article says this isn’t a strong point because good tools can do more than just say yes or no.

Some things are still true: real-world systems are messy, and not everything needs strict checking. But as software becomes more important, having ways to check it becomes more useful. The article agrees that software reliability is about more than just proofs—it’s also about good engineering and teamwork.

Next, we look at new AI models that are smaller and use less memory. These models are better at math and code, but not as good at remembering facts. Earlier, bigger models like GPT-4 had more parameters and could store more facts. Now, smaller models solve problems by using clever methods instead of just remembering lots of facts. Some models that fit on a normal computer GPU can beat much larger models on reasoning tests.

Facts take up a lot of space in a model, and they go out of date quickly. For example, a model trained in 2024 would soon be wrong about new libraries or news. But reasoning skills do not get old. So, new models get facts when needed, using web search or reading documents. This makes the model smaller and faster, and you can run it on your own computer.

Another benefit: when a model makes up a fact, it’s hard to fix. But if the model uses outside sources and cites them, mistakes are easier to spot and fix. This is more like a normal bug in code.

In the comments, some people like that models can be kept up-to-date with fresh data, not just old memories. But there are still questions about how well a model can “reason” without knowing many facts up front. Some say this is like how humans work: we look things up instead of remembering everything. But models will still sometimes mix facts from different places, so careful checking is needed.

Now, let’s talk about some computer history. The Intel Pentium MMX chip from 1997 brought SIMD—Single Instruction, Multiple Data—to regular desktop computers. MMX added 57 new instructions that let the CPU do the same operation on several pieces of data at once, which helped with graphics, audio, and video. MMX used special 64-bit registers, which were actually the same as the floating-point registers, but only used the lower 64 bits. This saved chip space, but meant you couldn’t use MMX and floating-point math at the same time.

With MMX, you could write code that added, multiplied, or shifted several numbers in one instruction. For example, adding eight pixels at once instead of one by one. It also had “saturating” arithmetic, capping values at 255 instead of wrapping around. MMX was not the first SIMD system—supercomputers used similar ideas before—but MMX made SIMD common for home computers. MMX didn’t support floating-point SIMD; that came later with SSE. To use MMX, software checked if the CPU supported it using the CPUID instruction.

Games in the late 90s used MMX for things like texture mapping and audio, but not as much as you might expect, since 3D graphics cards were taking over. MMX became less important after Intel released SSE and SSE2, which were more powerful and flexible. MMX was a short but important step in the journey to modern SIMD.

In the comments, many recall writing assembly code for MMX or learning about SIMD back then. Some say MMX made them think differently about programming, seeing data as groups instead of single values. Others point out MMX’s main problem: it couldn’t do floating-point math and SIMD together. Many remember the “EMMS” instruction you needed to switch back from MMX to floating point, and the bugs that happened if you forgot it. Some say writing MMX code by hand was fun but tricky, and now compilers can often do similar optimizations. Others note MMX was a stepping stone that helped bring advanced computing ideas to everyday programmers.

Next, MathCode is a new AI tool that helps people turn math problems in simple words into formal Lean 4 code and tries to prove them. The tool works on macOS and Linux, and lets users interact with it through the terminal or a browser. You can ask MathCode to prove math statements, and it will write a theorem in Lean, try to prove it, and save the result. It keeps a fast Lean REPL running, so checking code is quick after the first startup. When a proof is found, it saves the theorem for later use. You can also save your own rules or assumptions, and MathCode will check them for mistakes.

MathCode connects to online databases to find useful math facts and lemmas, helping it solve harder problems. It shows how theorems connect in a graph using Obsidian, helping users see how ideas build on each other. If a proof fails, it tries other ways and keeps going until it succeeds or gives up. For tricky problems, it splits them into smaller pieces and solves each one, then puts the answers together. The tool is open-source and based on earlier projects in automated math proving.

In the comments, many are excited to see AI helping with formal math proofs, saying it could make math easier for everyone. Some worry about the tool only working on macOS and Linux, hoping for a Windows version. Others ask if MathCode could help students, or if it’s mostly for experts. Some discuss Lean 4, saying it is powerful but hard to learn, so a good assistant is helpful. There are questions about how well the agent understands natural language math questions and if it can always give correct answers. Some like the idea of saving theorems for later, saying it could build a big knowledge base. Others want to know how MathCode compares to similar tools like Coq or Isabelle. Some are curious about the Obsidian graph for showing how math concepts link together. Most comments are positive and interested in seeing how MathCode grows.
