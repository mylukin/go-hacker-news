## Watching Go's new garbage collector move through the heap

- 原文链接: [Watching Go's new garbage collector move through the heap](https://theconsensus.dev/p/2026/07/19/observing-gos-garbage-collector-old-and-new.html)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49045474)

This article looks at how Go’s new garbage collector, called Green Tea, works and how it manages memory. The author explains how Go puts objects of the same size next to each other in memory, and how the garbage collector (GC) cleans up unused objects. The article compares Go’s approach to C#, shows code examples, and measures performance.

First, the author shows that Go groups objects of the same size together in memory. This makes it easier to see how memory is used. When the GC runs, it does not move objects, so they stay in the same place. In contrast, C# does not group same-size objects together, and sometimes moves objects during garbage collection.

The article explains how Go’s garbage collector works. It first “marks” live objects by following pointers from root objects. Then, in the “sweep” phase, it frees memory used by objects that are not marked. Go’s new Green Tea GC scans memory spans more efficiently, queuing up work instead of following every pointer directly. This new method should help the program run faster and use the CPU cache better.

To test this, the author builds a program that creates many linked objects, either packed tightly or scattered randomly in memory. By measuring cache misses and program speed before and after Green Tea, the author finds that the new GC makes the program faster. However, at first it looks like cache misses increase. After measuring more carefully, especially looking at L1 cache, the author finds that the new GC really does improve cache usage, especially in the L1 cache.

Next, the author shows a weakness of Go’s garbage collector: it cannot move objects to compact memory. If you delete 90% of your objects, Go cannot shrink memory usage as much as you’d expect, because the survivors are scattered. The program shows that memory is still “pinned” and not released to the OS, even though most objects are gone. But if you manually copy the survivors into a new packed array, Go can reclaim memory, and usage drops as expected. In C#, the garbage collector can move objects and compact memory on its own, so memory usage drops after deleting objects.

In the Hacker News comments, many people liked the clear examples and visualizations. Some users said it helped them understand Go’s memory model better. Others pointed out that Go’s non-moving GC design makes it easier to write safe and fast code, but has trade-offs like fragmentation. Some users wished Go would add a moving or compacting collector, but others argued this would break existing Go code that depends on stable pointers. A few developers shared tips for manually compacting data in Go, as shown in the article. Several commenters discussed whether the performance boost from Green Tea matters for most programs, or only for large server applications. Some pointed out that most real-world Go apps do not run into the fragmentation issue often, while others shared stories where it caused problems. There was also debate on whether C#’s moving collector brings more benefits or more complexity. A few users noted that Go’s GC is improving steadily and praised the Go team for making these changes. Some suggested more tools to help developers spot fragmentation in their programs. Others reminded readers that manual memory management is always possible, but should be used with care.

## Ray tracing massive amounts of animated geometry using tetrahedral cages

- 原文链接: [Ray tracing massive amounts of animated geometry using tetrahedral cages](https://gpuopen.com/learn/ray-tracing-massive-amounts-animated-geometry/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49021007)

This article talks about a new way to do ray tracing for scenes with many moving objects, like trees, grass, or crowds. It explains a method that helps computers show lots of animated things quickly, without using too much memory or taking too long to process.

Normally, when you animate many objects, the computer has to keep updating the shapes and the data that helps find which parts of the shape the light or rays hit. This is slow and uses a lot of memory, especially if each object is different and has many triangles. The new method uses something called a “tetrahedral cage.” Instead of changing every triangle when animating, the method puts a simple cage (made from tetrahedrons, which are like 3D triangles) around the object. The object is split into small pieces, each linked to a part of the cage. The computer only animates the cage, not all the triangles.

When a ray hits an animated object, the ray is transformed into the cage’s original shape, so it can check for hits using the static (unchanged) shape. This saves time because the small pieces and their data (mini-BLASes) do not need to be updated every frame. Many objects can share the same static data and only need their own cage movement. This is good for scenes with a lot of similar things moving in different ways.

The article shows that this method can render a scene with 585 million moving triangles at 60 frames per second on a modern AMD graphics card. It says the method is best for things like plants, crowds, or distant characters, where the shape does not change too much. It might not work as well for sharp movements or if the object’s shape changes a lot. There is a trade-off: using a simple cage is faster but less accurate, while a detailed cage is more accurate but slower.

The article also mentions that this new method can work with other ray tracing systems, like Microsoft’s DirectX Raytracing, and that AMD will release more tools and code for developers soon.

In the Hacker News comments, some people say this is a smart way to handle lots of animated objects and are impressed by the speed and memory savings. Others note that this is not a perfect solution for every case—if you need very detailed or special animations, you might need a different method. A few readers wonder how hard it is to make these cages for different shapes or how well the method works with really complex animations. Some users like that the technique allows sharing data between objects, which can save a lot of resources in big games or films.

There are questions about how visible the animation errors are when using a coarse cage, especially up close. Some think the method is very useful for background objects where details do not matter as much. Others suggest combining this with other tricks to get better results for important characters. A few people point out that similar ideas have been tried before, but this version looks more practical for real-time graphics. Finally, some comment that it is good to see more open-source research and hope for easier tools in the future.

- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49020993)

A new glue called Cyclic FP-fmoc can stick very well to nonstick surfaces like Teflon, but it can also be wiped off completely with ethanol. This glue is special because most strong glues are hard to remove and can damage surfaces, while weaker glues don’t hold well.

Cyclic FP-fmoc is a small-molecule adhesive made by scientists in Japan. It is a white crystal that melts and can be placed between two Teflon plates. After cooling for just 10 minutes, the plates stick together so well that they can lift 8 kilograms. In tests, this glue was much stronger than regular epoxies, acrylics, or silicones. The glue works by bonding to Teflon through strong connections between fluorine atoms, and it holds itself together with hydrogen bonds and special stacking of its ring-shaped molecules. 

The best part is that the glue can be removed completely just by washing with ethanol, leaving the surfaces clean. After removal, the same glue can be used again and still keep its strength. Because ethanol is common in hand sanitizer, people could use sanitizer to remove the glue in real-life situations. Another big advantage is that this glue can be recycled many times, which is a big problem for normal glues.

Some scientists not involved in the study think this glue could help recycling, especially for things like wind turbines or airplanes, where different materials are glued together. Normally, it is hard to recycle these things because the glue is hard to remove.

## Securing Services with Rootless Containers

- 原文链接: [Securing Services with Rootless Containers](https://blog.coderspirit.xyz/blog/2026/07/06/securing-services-with-rootless-containers/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49021024)

This article talks about using rootless containers to make running services like databases more secure. It explains that running containers as root (the most powerful user on Linux) can be risky because if someone escapes the container, they might control the whole system.

The article says many people think containers are secure by default, but this is not true. The main safety tools containers use are cgroups (for resource limits) and namespaces (for isolation), but these are not enough for strong security. If a container runs with root and gets hacked, the attacker can become root on the host, too. Real examples, like the CVE-2025-9074 bug, show this can happen.

Rootless containers use Linux user namespaces to map the root user inside the container to a normal, unprivileged user outside. This means if someone breaks out, they only become an unprivileged user on the host. The article uses Podman, which works without a root-running background service, making things safer. It describes how to set up a service (like PostgreSQL) to run under a special user, use systemd unit files for service management, and make sure the service keeps running even if no one is logged in as that user. It gives examples of setting up environment variables, checking service status, and controlling the service with systemctl commands.

The article also shows another example (Anubis) and adds more security tips: make the container’s filesystem read-only, don’t allow new privileges, and remove all Linux capabilities if not needed. It explains that rootless containers need special care for networking, especially when handling privileged ports and firewall rules. The author plans to write more about networking in the future.

In the comments, some people agree that rootless containers are a good idea and share their own tips for using them. Others say rootless containers can be tricky to set up, especially for new users or in complex systems. One user points out that some features may not work without root, or might need extra configuration (like mapping ports below 1024). A few mention that Podman is a good choice because it’s daemon-less, but Docker is improving rootless support too. Some warn that rootless containers are not a full solution—kernel bugs and misconfigurations can still cause problems. Others ask for more step-by-step guides or scripts to make setup easier, especially for teams with many services. One commenter wonders if rootless containers slow things down, but replies say the performance impact is small for most cases. A few users discuss using rootless containers with Kubernetes, noting that it works but can be complex. Some suggest extra security tools like seccomp or AppArmor, while others think rootless containers should be one part of a bigger security plan.

## The computer that helped win World War II

- 原文链接: [The computer that helped win World War II](https://spectrum.ieee.org/colossus-computer-ieee-milestone)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49012309)

This article tells the story of Colossus, the first large-scale programmable electronic computer, and how it helped the Allies win World War II. During the war, the Germans used a new encrypted communication system, more advanced than Enigma, called the Lorenz machine (codenamed “Tunny” by the British).

The British first heard this “strange new music” in 1941—fast, rhythmic code instead of Morse. Breaking this code was very hard. A team at Bletchley Park, including Alan Turing, Bill Tutte, and Tommy Flowers, worked to solve it. Bill Tutte figured out how the Lorenz machine worked, just by studying messages. Turing created a method called “Turingery” to find the machine’s settings from the coded messages. But the process was slow and only worked if German operators made mistakes. As the Germans improved their security, a faster way was needed.

Tommy Flowers, an engineer, built Colossus—using about 2,000 vacuum tubes, even though many experts thought it would not work. Colossus could read coded messages at high speed from punched tape, count and sort patterns, and help find the right settings for decryption. The first Colossus started working in early 1944. Soon, more machines were built; by the end of the war, there were 10 Colossi at Bletchley Park. These computers gave the Allies access to top-level German military plans—sometimes even messages signed by Hitler. This intelligence helped the Allies plan D-Day and other operations, and may have shortened the war by months, saving millions of lives.

After the war, almost all Colossus machines were destroyed for secrecy. Only two survived. Today, Colossus is honored as an IEEE Milestone, with a plaque at Bletchley Park recognizing its role in computing history.

In the comments, some people are amazed at how Colossus was built in secret and with so little recognition for years. Others compare Colossus to modern computers, noting how far technology has come but also how many basic ideas (like using binary code and programmable logic) started with these early machines. Some comment on how Colossus was not a general-purpose computer like ENIAC, but was still programmable for its tasks. A few users discuss the importance of people like Bill Tutte and Tommy Flowers, who don’t get as much attention as Alan Turing. There’s debate about whether Colossus or ENIAC deserves the “first computer” title, but most agree that Colossus was a key step in computer history. Some also reflect on the secrecy after the war, and how it delayed public knowledge about Colossus’s achievements. A few mention visiting Bletchley Park and seeing the rebuilt Colossus, saying it’s an inspiring experience. Many express respect for the engineers and codebreakers who worked long hours, often without knowing the full importance of their work. Overall, readers see Colossus as a symbol of clever engineering, teamwork, and the power of computers to change the world.

## Bytecode-to-Source Mapping

- 原文链接: [Bytecode-to-Source Mapping](https://tidefield.dev/bytecode-to-source-mapping/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49073665)

This article is about how to map bytecode offsets back to source code lines, which helps when debugging or reporting errors in a virtual machine (VM). The author explains different ways to store and look up line numbers for each bytecode instruction, using examples from the book "Crafting Interpreters."

First, the simplest way is to keep an array of line numbers, one for each byte of bytecode. This is fast for lookups but uses a lot of memory. To save memory, you can use run-length encoding: instead of repeating the same line number many times, you store each line number once, along with how many bytes use it. This saves space if many bytes come from the same source line, but now you have to search through the runs to find the right line number.

To make searching faster, you can store the starting offset for each run, paired with its line number. With this, you can use binary search to quickly find the line for any bytecode offset, making random lookups much faster. For sequential tasks, like disassembling bytecode, you can use a simple cursor that advances through the runs, making the process efficient.

The article compares the memory and speed trade-offs of these methods in a table. It also looks at how popular VMs do this. The Java Virtual Machine (JVM) keeps starting offsets and line numbers, but usually searches through them with a linear scan. Lua keeps line numbers in a parallel array, but stores only changes (deltas) from the previous line, plus checkpoints, to save space.

In the comments, many people praise the clear explanation and say they faced similar problems when building interpreters or debuggers. Some point out that memory use is usually not a problem for small VMs or scripts, but fast lookup is important for big programs or tools that need to show errors quickly. Others discuss how real-world VMs sometimes use even more advanced data structures or compress the line tables further. A few mention that in production, keeping line number information is optional, and some VMs drop it to save space or for security.

Some readers share tips from their own projects, like using hash maps or hybrid systems that mix fast lookups with compressed storage. Others warn that with inlining or code transformations, mapping back to source lines can be tricky or even impossible. A few people also say that the choice depends on your main use case: if you mostly want to step through code, sequential access is enough; if you want to show stack traces, fast random lookup matters more. Overall, the discussion shows there is no one-size-fits-all answer, but understanding these methods lets you pick what works best for your VM.

## Judge Rejects Google's Attempt to DMCA Its Way Out of Being Scraped

- 原文链接: [Judge Rejects Google's Attempt to DMCA Its Way Out of Being Scraped](https://www.techdirt.com/2026/07/27/judge-rejects-googles-attempt-to-dmca-its-way-out-of-being-scraped/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49073513)

A judge has thrown out Google’s lawsuit that tried to use DMCA laws to stop another company, SerpAPI, from scraping Google’s search results. Google wanted to say that SerpAPI was breaking copyright law by getting search results in ways Google didn’t like, but the judge did not agree.

The article explains that Google built its own business by scraping the open web, but now wants to stop others from doing the same to Google. In recent years, companies want to put more controls on public data, especially because AI needs so much data to learn. SerpAPI collects search results and offers them to others as an unofficial API. Google claimed SerpAPI was breaking the DMCA’s “anti-circumvention” rule, which is meant to stop people from breaking digital locks on copyrighted content. Google’s “SearchGuard” is a protection tool, similar to a CAPTCHA, that tries to block bots from scraping search results. 

The judge said that most of Google’s search results are just public information, so copyright law does not apply. Only some results, like images in the “Knowledge Panel,” might be protected, but Google did not prove this is true for all results. The court said that using SearchGuard to block access to public data is not a good reason to use DMCA laws. The judge pointed out that DMCA 1201 is about stopping people from getting around real protections for copyrighted works, not stopping access to public information. 

The judge dismissed all of Google’s main DMCA claims, though Google could try again with a much smaller argument, focused only on search results that really do have copyrighted content.

In the comments, many people are happy about the judge’s decision. Some say Google’s behavior is hypocritical, since Google used to depend on scraping other sites. Others are worried big companies will use copyright laws to control the open web. Some think scraping is a “gray area,” but agree that public search results are not really copyrighted. A few people point out that if Google wins such cases, it could become harder for small developers and researchers to access online data. Others mention that DMCA 1201 has been used in bad ways before, like stopping people from using third-party printer ink, and they are glad to see courts pushing back. Some commenters hope this case will help keep the web more open. But a few warn that Google may come back with new lawsuits, and the fight over scraping is not over yet. Overall, most agree this is a win for open web access and for developers who need to use public data.

The hacker reported this problem to the company in November 2025. At first, the company did not reply, but after a few weeks, they fixed the main problem and closed the open APIs. The hacker tried to tell them about other smaller issues, but could not reach anyone interested. He decided to write about his findings after waiting several months.

The article includes details, screenshots, and links to the APIs and responses, showing just how much data was open.
