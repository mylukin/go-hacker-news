## Go 1.27

- 原文链接: [Go 1.27](https://go.dev/blog/go1.27)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49365405)

Go 1.27 is now released, bringing many new features to the Go programming language. This update adds changes to the language itself, improvements to tools, better performance, and new features in the standard library.

One big change is that Go now supports generic methods. Before, you had to write a new method for every type, but now you can write one method for all integer types. Another update lets you use keys from embedded structs directly when making a new struct, which makes code simpler. Also, function type inference is better. Now, Go can guess the type you want to use in more places, so you don’t have to write it out every time.

The tools got better too. The `go fix` command can now help modernize your code in new ways. The `go doc` command can show docs for packages at a specific version. The `go mod tidy` command cleans up your module files more smartly.

For performance, small memory allocations are now up to 30% faster. There’s also a new tool to find stuck goroutines, which helps with debugging.

The standard library has new things as well. The `encoding/json` package is now faster and has new options. There’s new support for a post-quantum signature algorithm, which adds more security. You can now work with UUIDs more easily. There is also new support for SIMD instructions, which can make some programs much faster. The HTTP testing package now has a new way to create in-memory servers for tests.

In the comments, many people are happy about generic methods, saying they make Go code much cleaner. Some users are excited about the improved JSON handling and the new UUID package, which was a common request. Others like the performance improvements, especially for server programs that create lots of objects.

A few developers wish some features had come sooner, like better type inference and JSON improvements, but they are glad to see them now. Some worry that new features might make Go more complex, but most agree that these changes are helpful. There is also discussion about the new post-quantum crypto support, with some saying it’s good to see Go keeping up with security trends.

A few commenters mention that the new `go fix` and `go doc` features will help teams keep their code up to date. Some people ask about backwards compatibility and are pleased that old code should still work. Others want to know more about the new experimental SIMD support and how it might help with performance-heavy tasks. Unsloth just released Dynamic 3.0 GGUFs, which are new files for running large language models (LLMs) like Qwen3.8-27B with better accuracy and smaller size. These files work with popular tools like llama.cpp and the Unsloth Desktop app.

Dynamic 3.0 uses improved quantization, which means the models keep more quality but use less space. The team made a better calibration dataset with more types of data, including coding, chat, and many languages. They do not use the calibration dataset for training, which helps avoid overfitting. Instead, they use post-training quantization (PTQ), and they share their calibration files so others can test or improve them.

Some smaller quantized models now save even more disk space by removing extra modules, and there are new super-small versions that keep decent accuracy while being much smaller. The new methods also do better on important benchmarks like Divergence-300 and KL Divergence, which are better ways to check model quality than just top-1% accuracy.

Unsloth is careful to avoid overfitting by testing on datasets not used for calibration. They also explain why KL Divergence is a better measure than just accuracy, since it checks if the model's outputs are close to the original full model. They built their own benchmark tools to make sure results are fair and not just lucky guesses.

The article also shares details about the older Dynamic v2.0, which already improved model accuracy and size. The new v3.0 is even better, with smarter ways to choose which parts of the model to quantize. They show test results for models like Gemma 3 and Llama 4, with tables comparing file size, accuracy, and efficiency.

Unsloth also fixed bugs in Llama 4 related to settings and normalization, which helped increase accuracy for everyone using those models. They give step-by-step instructions to run these models with their quantized files.

Some are excited about the real improvements in model accuracy and size, calling it a big step forward for running LLMs on smaller hardware. Others ask questions about how the new quantization compares to other providers, and if the gains are real in daily use.

A few commenters worry about overfitting or possible hidden tricks in the benchmarks, but the Unsloth team replies with their testing methods and open-source files, which builds trust. ## Unlocking a locked/deactivated e-waste Cricut Maker

- 原文链接: [Unlocking a locked/deactivated e-waste Cricut Maker](https://sprocketfox.io/xssfox/2026/07/01/cricut-unlock/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49365841)

This article is about fixing a locked Cricut Maker machine found in e-waste, which is a type of cutting machine often disabled by the company when resold or replaced. The writer noticed the machine looked okay except for worn-out rollers and decided to see if it could be used again.

First, the writer learned that Cricut often locks machines so they can’t be used again after being replaced or resold. The machine found was locked, showing a “Machine deactivated” message. Replacement rollers were cheap and easy to find, so the physical fix was simple. The power supply for the machine was also changed from 18V to 12V, but it still turned on and did a self-test.

To unlock the device, the first idea was to look for a memory chip (EEPROM) on the motherboard to change the serial number, but there was no easy way to do this. The second idea was to intercept the network traffic and trick the Cricut software by changing the serial number or the response message, but security features made this too difficult.

The writer then decided to intercept the USB connection between the machine and the computer. By using a USB analyzer (Wireshark), the writer discovered how the serial number was sent. Using a Raspberry Pi RP2040 microcontroller and some example code, a device was built to sit between the Cricut and the computer. This device changed the serial number in real time, so the software thought the machine was valid and unlocked. Once this was set up, the machine worked like new and could even be registered with fake serial numbers.

The article points out this method could let anyone lock or unlock other people’s machines if they knew the serial numbers, and this is a security problem.

Finally, the author lists other ways to unlock Cricut machines, including intercepting network traffic, writing new drivers, or patching the firmware, but decides not to try them because the current solution works. The author does not share the code for legal reasons, but says it’s based on public Arduino examples.

People in the comment section had mixed feelings. Some were impressed by the technical skill and happy to see e-waste being reused. Others criticized Cricut for locking devices and making them hard to repair, saying this kind of control is bad for users and the environment. A few worried about security and how easy it might be for someone to take over another person’s machine. Some commenters shared their own stories about fixing or hacking locked devices, while others suggested it would be better if companies made unlocking easier. There were also questions about the legal risks and if sharing the unlocking method could get someone in trouble. A few people asked for more details or code, but others agreed it was smart not to share due to possible copyright issues. Some suggested that communities should work together to find better repair solutions for locked hardware. Overall, most people liked the creativity and effort to keep old tech useful.

## DFlash 2: Keep Drafting Parallel

- 原文链接: [DFlash 2: Keep Drafting Parallel](https://inco.ai/blog/dflash2/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49366792)

The article is about DFlash 2, a new way to make large language models (LLMs) faster by improving how they generate text. It explains how DFlash 2 helps AI agents write more quickly and cheaply, which is important as agents now use many more tokens than simple chatbots.

DFlash 2 builds on the idea of speculative decoding. In this method, a smaller draft model guesses several words at once, and the big model checks if the guesses are right. If the guesses are good, you can save time by verifying many words in one go. The first DFlash version already let the draft model guess all positions in parallel, making things fast. DFlash 2 goes further—it gets over 20% more output per verification pass, with almost no extra delay.

To do this, DFlash 2 uses two tricks. First, it doesn’t just keep the best guess for each word; it keeps the top 16 choices at every position. Then, it uses a simple scoring method to pick the most likely path through these guesses, so the whole block of words is more likely to make sense together. This “path selector” is much lighter and faster than previous methods that tried to fix guesses one by one.

Second, DFlash 2 uses a tiny convolution (a kind of local smoothing) to help the model keep track of short-range connections between words inside each block. This helps fix the “suffix decay” problem, where guesses get worse at the end of a block. The improvement is almost as good as making the model much deeper, but with far fewer new parameters and almost no slow-down.

The article shows that DFlash 2 beats other methods like DSpark and MTP on many benchmarks, giving about 20% more accepted tokens per pass and making models up to three times faster than the old way. It’s already available for popular models and tools, and getting started is as easy as running a few commands.

In the Hacker News comments, many people are impressed by the speed improvements and the technical details. Some think speculative decoding is the future for LLMs, as it can reduce costs and energy use, which is important for big AI deployments. Others say that while these tricks help a lot, the real bottleneck may move elsewhere in the system, like memory or networking, as inference gets faster.

A few commenters ask about how DFlash 2 compares to other parallel decoding methods, like those from Google or NVIDIA. Some share tips on getting DFlash 2 running with their favorite frameworks, and others report good results trying it out. There are questions about how much the quality of the output changes, but the article claims the results are exactly the same as before.

One person wonders if this approach can help with smaller, local models, and others are excited to see open-source support. A couple of people discuss the math behind the “path selector” and suggest there is even more room to improve. Some are cautious, saying that while speed is great, it’s important not to break compatibility or stability.

Overall, the community is very positive. Many feel DFlash 2 is a big step forward for LLM serving and are eager to use it in their own projects or businesses.

## The little-known winstart.bat batch file

- 原文链接: [The little-known winstart.bat batch file](https://devblogs.microsoft.com/oldnewthing/20260811-00/?p=112605)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49314109)

The article explains what the winstart.bat file was in Windows 95 and older Windows versions. It compares winstart.bat to autoexec.bat, showing when and why each runs during the computer’s startup.

First, when a computer started, MS-DOS loaded and ran autoexec.bat, which could install small programs called TSRs. Next, Windows would start and create a special “system virtual machine.” Before Windows finished starting, it would check for a winstart.bat file. If it found one, it would run it inside this virtual machine. This allowed users to install more TSRs, but these TSRs would only affect Windows programs, not the MS-DOS ones. For example, you could load network drivers just for Windows, keeping more memory free for DOS games or programs. The article shows that winstart.bat is older than many think—it was already in Windows 3.1, not just Windows 95. There’s even a table from the Windows 3.1 Resource Kit showing which TSRs are visible in Windows or in DOS virtual machines, depending on where you load them. The main point is that winstart.bat gave users control over what programs and drivers ran under Windows versus DOS, which was helpful for memory and compatibility.

In the comments, some people say they never knew about winstart.bat and wish they had known earlier, especially because it could have helped with tricky DOS and Windows compatibility problems. Others remember using autoexec.bat but never needing winstart.bat, since they mostly ran DOS programs. A few commenters share stories about trying to manage limited memory in old computers, saying tools like winstart.bat could help save space. Some debate if winstart.bat was well documented; a few think Microsoft should have made its use more clear, while others point out it was in the Resource Kit manuals. There’s also talk about how Windows 95 and earlier managed virtual machines, with some nostalgia about how creative people had to be to get things working. A few technical users explain that loading network drivers only in Windows was important because some drivers could crash if run in multiple virtual machines. One commenter jokes that using Windows in those days sometimes felt like hacking your own system. Overall, readers find the explanation helpful and enjoy learning about this “hidden” Windows feature.
