接下来是一项老服务的告别。根据保存下来的网页，BugMeNot 已经关闭，页面只留下简短的话：“感谢每一位曾经设想过更好互联网的人。”

BugMeNot 让用户分享网站登录信息。想读一篇文章时，访客可以试试别人提供的账号，而不是先注册自己的账号，也不必每次都交出个人邮箱。它的想法很直接：少建几个账号，少一点麻烦。

当然，共享登录并不保证长期有效。密码可能被改，网站也可能封掉账号。它是一条方便的近路，而不是稳定访问的承诺。

告别页面没有说明关闭原因，没有提到运营成本、法律问题或管理团队，也没有推荐替代服务。因此，这些都不能被当作停运原因。那句关于更好互联网的话，也没有进一步展开。可以确定的是，对使用过它的人来说，绕过不必要注册的办法又少了一种。

这件事值得从几个方向看。读者可能在意打开页面的速度，也可能更看重少交一些个人信息；网站经营者则可能认为，账号有助于运营和支持服务。

共享账号本身也有风险，因为陌生人同样可以使用那些登录信息。临时邮箱或许能减少暴露真实地址的需要，却仍然省不掉注册步骤。对开发者来说，一个直接的问题是：网站只是让人阅读基本内容，真的需要账号吗？如果确实需要，能否把注册做得清楚、有用，而不是让访客先去找绕路的办法？

从访问网站转到发送邮件，Spamhaus 正从 2026 年 11 月开始，逐步加强对邮件发送方的检查。邮件服务会使用它的封锁名单来帮助拦截垃圾邮件，因此配置不佳的发送方可能面临邮件被拦的问题。

具体来说，每个发信 IP 地址都必须有反向 DNS 记录，指向一个完整的服务器名称；这个名称也必须能正向解析回同一个 IP 地址。

服务器在 HELO 或 EHLO 问候中使用的名称，需要保持稳定，并指向发信地址。“localhost”和主机服务商的默认名称都不符合要求。IPv6 发送方同样需要有效的反向 DNS，并且地址块至少为 /64。

更广泛的指南还包括几项身份检查。SPF 记录要说明哪些服务器可以代表域名发信；每封外发邮件都要有有效的 DKIM 签名；域名还要公布 DMARC 策略，告诉收件服务如何处理身份检查失败的邮件。

邮件列表也有要求：订阅者必须先确认自己的邮箱地址，才能继续接收邮件。购买或收集来的地址列表可能藏有垃圾邮件陷阱，也就是专门用来发现不受欢迎邮件的地址。

发送方应该逐步增加发信量，不能使用制造虚假打开或回复的服务。投递失败率必须低于百分之五。商业邮件还需要提供简单的退订方式，并在两天内处理退订要求。Spamhaus 提供了工具，用于检查服务器问候、DNS 配置，以及地址或域名是否进入名单。

这些规则带来的讨论，不只是“要不要反垃圾邮件”。小型邮件服务器的运营者可能担心配置负担，有经验的管理员则可能认为，这些本来就是基本要求。经常收到垃圾邮件的人可能欢迎更严格的检查，但一个合理的问题是：如果垃圾邮件发送者也能把 DNS 配对，这些检查能解决多少问题？

共享主机用户还需要考虑，同一服务上的其他发送方会不会带来影响。新企业可能质疑另一条建议：新域名在用于发邮件前先等三十天。重视隐私的人，也可能不认同不要隐藏域名所有者信息的建议。

至于确认订阅和方便退订，对不想收到邮件的人显然很重要。开发者现在可以先查一件事：自己的主机服务商，是否允许控制这些规则需要的全部 DNS 设置。

下面进入开发工具。第一篇文章来自一位使用 Rust 超过六年的作者。他的核心体会是，学习一种不同的语言，改变的不只是代码写法，还有思考软件的方式。

先看 enum。Rust 可以用一个类型表示几种不同的数据，例如人或者猫，并由编译器检查代码是否处理了所有情况。如果情况数量有限，而且事先已经知道，这有时比搭建一套共用接口更简单。

Rust 也可以在程序运行前，为具体类型生成对应代码，从而省去运行时的一部分检查。作者因此越来越习惯用类型帮助规划软件，就像用测试和清楚的说明来帮助设计一样。

让他最意外的则是宏。宏可以在程序运行前生成代码。使用 Serde，增加几行声明，就能生成保存和读取数据所需的代码；使用 Clap，一个类型定义就能描述命令行选项，并生成帮助文字。

所有权规则也改变了他的设计习惯。它要求开发者认真思考：哪些部分控制数据，哪些部分可以修改数据。这些规则学习起来可能不容易，但作者认为，它们也能让整体设计更好理解。

面对树这类相互连接的数据，他常把元素集中放进数组，再用数字来连接，而不是直接互相引用。这种方式还可能改善内存使用和数据访问速度。

他的最大收获是，性能提升不只是让原来的任务快一点。有时，速度会让原本不可行的软件变得可行。

围绕这些经验，可以提出不少实际问题。编译前发现遗漏情况的检查很有吸引力，但小项目是否值得付出 Rust 的学习成本？其他语言也有不少类似思想，作者自己也承认这一点。如果数据种类需要经常扩展，共用接口是否反而更合适？

宏可以减少重复劳动，但生成出来的代码是否容易理解？所有权规则究竟是设计上的帮助，还是额外的工作？用数组保存连接关系时，删除元素后又该如何安全处理编号？

最后还是要回到项目本身：什么时候更快的运行速度真的打开了新机会，什么时候一个更简单的方案就够了？

说到 Rust，还有 Jiff 1.0。这是一个日期与时间库，目标是让常见错误更难发生，目前已经用于 Cargo、uv 和 Nushell 等工具。

Jiff 的核心做法，是把时区放在日期时间处理的中心。时间戳代表一个确定的时刻，而本地日期和时间，描述的是人们在钟表上看到的内容。Jiff 可以通过纽约、东京这样的时区，把两者联系起来。

时区不只是与 UTC 相差几个小时，它还包含调整钟表的规则。当时钟切换时，有些本地时间会出现两次，有些则根本不存在。

默认情况下，Jiff 会选择重复时间中的第一次；遇到不存在的时间，则向前移过缺口。开发者可以更改这些选择，也可以要求直接报错。

它还知道，“明天的同一时间”不一定是二十四小时之后，也可能相隔二十三或二十五小时。它的 Span 类型把月、日等日历单位，与小时、分钟分开处理，因此，加一个月不会被简单当成加上固定数量的秒。

Jiff 支持常见日期格式的读写，也能处理“二小时三十分钟”这类容易阅读的时长。其他语言和历法的支持，则通过独立的 ICU4X 库提供。作者计划保持 1.0 的设计稳定，除非发现严重问题。

对应用开发者来说，少一些时钟切换问题很有价值；对库的维护者来说，不轻易破坏兼容性也很重要。不过，已经使用 Chrono 或 time 的团队，仍然需要判断迁移是否值得，也可能选择继续使用现有工具。

把本地时间和确定时刻分开，有助于理解问题，却不会替产品决定业务规则。会议和预约应用，仍然要明确重复或缺失的时间该怎么算。面向全球用户的团队，还可能需要额外的语言和历法支持。

如果只是测量代码运行了多久，文章建议使用 Rust 自带的 Instant。先分清需求：你处理的是人类日历，还是单纯经过了多少时间？

接下来看看浏览器图形。有一位作者希望让 Three.js 的光照接近大型游戏。这份报告区分了已经能用、正在评审，以及仍然缺少的部分。

整体方案先为不移动的物体保存光照。移动物体则从场景附近的采样点获取光照信息。每个房间还会保存自己的反射视图，让红色房间里的物体反射红墙，而不是错误地映出天空。

通过改进表面方向的存储方式，反射可以在不增加内存的情况下变得更平滑。另一些效果则利用屏幕上可见的信息，补上反射、柔和阴影，以及物体之间反弹的光。

但屏幕效果看不到整个场景，因此仍然需要预先保存的光照来填补空缺。目前最大的缺口，是让这些不同来源的光，都能进入每个表面的光照计算。

这样，粗糙、光滑和金属表面才能作出正确反应，而不是等画面完成后，再往上加一层亮光；同时也能避免把同一束光算上两次。

方案还会利用上一帧的颜色，让部分效果在新场景绘制前运行。结合多帧信息可以减少噪点，但必须控制错误，不能让错误随着时间不断累积。

先绘制较少的像素，再生成更大的最终图像，可能节省时间和内存，不过还没有放进完整方案测试。而且，新方法不一定更快：一次早期测试中，更聪明的反射搜索反而让场景变慢了。

这里的讨论重点，应该放在完整体验上。网页开发者和小型游戏团队，可能欢迎在熟悉的浏览器工具中获得更好的画面；面向手机的团队，却可能更关心内存和速度，甚至宁愿使用简单但稳定的预存光照。

正确组合光源，在图形计算上很重要，但玩家也会在意移动时有没有模糊和拖影。库的使用者还需要问：这些变化会不会让 Three.js 更难学习和维护？

开源评审的价值，正在于让新功能能够协同工作。真正判断它离大型游戏还有多远，最好还是等一个完整演示，并在多种设备上测试。

从大型场景缩小到一个图标，下一篇文章讨论的是 squircle，也就是介于方形和圆形之间的形状。

它并没有唯一的画法。一个常见版本是超椭圆，调整公式中的一个数字，就可以让形状从圆逐渐接近方形。有些版本用一条连续曲线围成整体，另一些则把直边和圆滑的角接起来。保留直边的好处是，形状可以变宽或变高，而不必改变角的形状。

苹果在 2013 年改变应用图标后，让这种形状得到更多关注。但苹果的图标有平直的边，并不是简单的超椭圆。

文章指出，苹果的形状存在一些很难察觉的小误差。Figma 修正了其中一部分，但它的曲线连接仍然不是完全平滑。

关键不只是线有没有接上，而是弯曲程度的变化是否平顺。文章介绍，超椭圆和另一种叫回旋线的曲线，可以提供更平滑的连接。CSS 现在也通过 corner-shape 定义这类圆角，文章展示了接近苹果设计的设置。

这种细节值得花多少力气？设计师可能看重柔和的视觉感受，即使多数人说不出差别；也有人会认为，变化太小，不值得过度投入。图形开发者则可能关心，小误差在大尺寸绘图中会变得明显。

网页开发者有了 CSS 选项，就不一定需要自己制作形状，但仍应检查浏览器支持。使用 Figma 的人，也可能更在意实现是否贴近设计稿，而不是曲线是否数学上完美。

文章还给出了比较不同形状的共用度量方法，对工具开发者有用。另外，给这种形状画边框，并不等于在里面放一个缩小版本那么简单。最终要问的是：最好的形状，是最精确的那个，还是最适合眼前用途的那个？

硬件方面，TRMNL 发布了 Frame：一块装在手工木框里的 31.5 英寸彩色 ePaper 屏幕。它用来展示艺术作品、照片、日程和天气，而不是扮演电视。

创始人把这款产品与早年的 ArtSpot 联系起来。那个项目曾把本地艺术作品放进咖啡馆，但销售并不顺利。TRMNL 过去也抗拒加入彩色，希望设备保持简单；后来，灰度图像取得的更好效果，帮助团队改变了想法。

Frame 可以按设定时间更新，不必每隔几分钟刷新，从而减少闪屏并节省电量。通过 microSD 卡，它可以完全离线工作，不需要把个人信息传到公司服务器。

设备带有可充电电池，背面额外提供 USB-C 接口，方便持续供电。团队还在开发名为 Lazarus 的色彩工具，称它能改善屏幕上的图像效果，并计划公开代码，让其他人修改。

Frame 可以横挂或竖挂，支架为选配。新的 Local Art 功能则让艺术家通过 TRMNL 分享和销售作品。公司在自己的工坊制作木框，并自行完成最终组装。

第一批大约有四百七十台，预计少量在 2026 年底发货，大部分在 2027 年初发货。

这类产品的吸引力，是换画时不用把家里变成一个电视屏幕。但实际印刷品可能仍是一些人的首选，彩色效果是否足够好，也需要实物判断。

完全离线对隐私很有意义，可修改的色彩工具也可能吸引开发者。展示日程的人，或许更喜欢按时更新，而不是频繁刷新。不过，日常使用的电池续航仍然是重要问题。

自有工坊可以成为卖点，新产品的交付时间也值得留意。对首批发货地区以外的买家，还要把运费和进口费用算进去。

最后，把目光从设备转到农田。康奈尔大学的研究人员研究了让羊与太阳能板共用土地的方式：农民可以获得收入，羊则负责吃草。

两篇新论文分别关注昆虫，以及牧羊生意的管理工具。

第一项研究在纽约州的一座太阳能农场进行了三年，比较不同放牧密度。每公顷两只羊时，有益昆虫的数量比机械割草区域多百分之三十八，其中很大一部分增长来自蜜蜂，蜜蜂数量增加了百分之八十三。

每公顷四只羊时，昆虫数量与机械割草区域相近，但草比两只羊的区域更短。

每公顷八只羊，控草效果最好，羊也保持健康；但这个密度下，蜜蜂数量下降了百分之四十五。结果呈现出一个清楚的取舍：把草控制得更好，不一定同时最有利于有益昆虫。

第二个团队开发了一份电子表格工具，帮助农民规划牧羊业务。它结合成本、预期收入、草料供应，以及农民希望维持的羊群规模，帮助决定什么时候买羊、什么时候卖羊。

工具也能帮助太阳能公司设计更适合农民的合同。已经有一家牧羊企业，在接纳新农民加入项目时使用它。这个模式的潜力很直接：农民可以通过让羊吃草获得报酬，而不是为了放牧先付土地使用费。

不过，不同参与者会有不同的重点。农民可能希望在卖羊收入之外，获得稳定的服务报酬；太阳能运营方则会比较，养羊控草是否比机器割草便宜。关心蜜蜂的人，可能更愿意少放一些羊，即使草会长一些。

研究只在纽约州一个地点进行，结果能否适用于其他地区，还需要检验。开发者可能欣赏电子表格这种简单工具，但也会想知道，它的计划与真实经营结果有多接近。

当地居民可能喜欢同一块土地同时生产食物和电力；谨慎的农民则需要把围栏、供水和转移羊群的费用一起算进去。

所以，问题不是羊越多越好，而是怎样找到一个数量，让农民、太阳能公司和昆虫都能受益。

今天的内容就到这里。从注册页面、邮件规则，到时间库、屏幕和牧场，这些故事都提醒我们：一个方案好不好，不能只看它解决了什么，也要看它把成本和麻烦留给了谁。
