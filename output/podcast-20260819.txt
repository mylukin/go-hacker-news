Next, Go 1.27 is now released, bringing many new features and improvements to the Go programming language. The update adds support for generic methods, so you can write one method for all integer types, instead of repeating code. You can now use keys from embedded structs directly, making code simpler. Function type inference is better, so Go can guess the type you want more often. Tools like go fix, go doc, and go mod tidy are improved, making it easier to modernize and manage your code. Small memory allocations are up to 30% faster, and there’s a new tool to find stuck goroutines for easier debugging.

The standard library also gets updates. The encoding/json package is faster and has new options, and there is support for a post-quantum signature algorithm, which adds security. UUIDs are now easier to use, and there’s support for SIMD instructions for faster programs. The HTTP testing package now lets you create in-memory servers for tests.

Now, let’s talk about a story of hardware hacking. Someone found a locked Cricut Maker machine in e-waste and tried to fix it. Cricut machines are often locked by the company when resold or replaced, showing a “Machine deactivated” message. The writer changed the worn-out rollers and fixed the power supply. To unlock the device, they tried looking for a memory chip to change the serial number, but couldn’t find one. Next, they tried intercepting network traffic, but security was strong. Finally, they intercepted the USB connection between the machine and the computer, using a Raspberry Pi RP2040 microcontroller. This device changed the serial number in real time, so the software thought the machine was valid and unlocked. The machine worked like new and could be registered with fake serial numbers.

The article points out this method could let anyone lock or unlock other machines if they know the serial numbers, which is a security problem. Other ways to unlock Cricuts are possible, but the author didn’t try them, and did not share the code for legal reasons.

In the comments, some people were impressed by the technical skill and happy to see e-waste being reused. Others criticized Cricut for locking devices and making repairs hard, calling it bad for users and the environment. Some worried about security, and a few shared their own stories about fixing locked devices. There were questions about the legal risks, and some agreed not sharing the code was smart. Many people liked the creativity and effort to keep old tech useful.

Next, we have DFlash 2, a new method to make large language models faster by improving how they generate text. DFlash 2 uses speculative decoding, where a smaller draft model guesses several words at once, and the big model checks them. DFlash 2 keeps the top 16 guesses at each position and uses a simple scoring method to pick the most likely path. This helps write more words per verification pass, with almost no extra delay. It also uses a small convolution to help the model keep track of word connections, fixing the “suffix decay” problem where guesses get worse at the end of a block. DFlash 2 gives about 20% more accepted tokens per pass and can make models up to three times faster than before. It’s already available for popular models and is easy to use.

In the comments, many are impressed by the speed improvements and technical details. Some think speculative decoding is the future for LLMs, as it reduces costs and energy use. Others ask about DFlash 2 compared to other methods from Google or NVIDIA. Some share tips and report good results, while others want to know if output quality changes. The article says results are the same as before. Some hope this approach can help smaller local models too. A few discuss the math behind the path selector and see more room to improve. Most people are positive and eager to use DFlash 2 in their own projects.

Finally, the article explains what the winstart.bat file was in Windows 95 and older Windows versions. It compares winstart.bat to autoexec.bat, showing when and why each runs during startup. MS-DOS loaded first and ran autoexec.bat, which could install TSRs. Then Windows would start and check for winstart.bat, running it inside a special virtual machine. This allowed users to install more TSRs, but these would only affect Windows programs, not DOS ones. For example, you could load network drivers just for Windows, saving memory for DOS games. Winstart.bat is even older than many think—it was already in Windows 3.1. The article includes a table showing which TSRs are visible in Windows or DOS, depending on where you load them. The main point is that winstart.bat gave users more control over drivers and memory.

In the comments, some people say they never knew about winstart.bat and wish they had, as it could have helped with tricky compatibility problems. Others remember using autoexec.bat but not winstart.bat, since they mostly used DOS programs. A few share stories about managing limited memory in old computers. Some debate if winstart.bat was well documented, with a few saying Microsoft should have made it clearer. There’s also talk about how Windows 95 managed virtual machines, with some nostalgia for how creative people had to be. Technical users explain that loading network drivers only in Windows was important, as some drivers could crash if run in more than one virtual machine. One person joked that using Windows in those days sometimes felt like hacking your own system. Overall, readers found the explanation helpful and enjoyed learning about this hidden Windows feature.
