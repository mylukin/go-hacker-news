## Postgres LISTEN/NOTIFY actually scales

- 原文链接: [Postgres LISTEN/NOTIFY actually scales](https://www.dbos.dev/blog/postgres-listen-notify-scalability)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49040296)

This article talks about how Postgres’s LISTEN/NOTIFY feature can actually scale well, even though many people think it does not. It explains how LISTEN/NOTIFY is used to let readers know when new data is written, which is useful for real-time or streaming systems.

The simple way to use LISTEN/NOTIFY is to have a trigger that sends a notification every time new data is written to a table. This works well for small workloads and gives low delay, but when things get busy, it quickly slows down. The main reason for this is that Postgres uses a global lock when sending notifications, so only one transaction can send a notification at a time. This lock is needed because Postgres wants to make sure notifications are sent in the right order, matching the order that data is written.

Because of the lock, writes with notifications cannot use some of Postgres’s usual tricks to go faster, like group commits. This makes the system slow even though the database does not look busy in terms of CPU or disk use—everything is waiting for the lock. 

To solve this, the team changed their approach. They noticed that the notification itself is not as important as the actual data in the table. So, they started to buffer notifications in memory and send them out in groups, not one by one. This way, the global lock is only needed once for the whole group, not every time new data arrives. If something crashes before the buffer is sent, readers can still poll the table every now and then, just in case a notification was missed.

With this new system, they reached 60,000 writes per second (20 times faster than before) and still kept the delay very low. Now, the database is finally using all its CPU, showing it is working as hard as it can, not just waiting on a lock.

People in the comments had mixed feelings. Some agreed with the results and said they also use LISTEN/NOTIFY in production, but with care. Others pointed out that while buffering helps, it is not a perfect solution, especially if you need every notification to be delivered without fail. Some users worried about lost notifications if the process crashes, though the fallback polling helps. There were comments about how LISTEN/NOTIFY is great for small systems or single-node setups, but may not be good for large, distributed systems. A few mentioned that upcoming changes in Postgres 19 do not fix the global lock problem, so this workaround is still needed. Some users shared alternative tools, like using message queues or external pub/sub systems, and said that for very high workloads, these might be better. Others liked that this solution keeps things simple and avoids extra moving parts, which is good for many apps. Some warned that every system has limits, and it is important to test for your own needs. Overall, people liked the clear explanation and the practical advice, but also reminded others to be careful and know when this approach fits or doesn’t fit their project.

## My security camera shipped a GitHub admin token in its login page

- 原文链接: [My security camera shipped a GitHub admin token in its login page](https://hhh.hn/hanwha-github-token/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49034292)

This story is about a person who found a big security problem in Hanwha Vision security cameras. The cameras’ software had a token that gave admin access to Hanwha’s GitHub accounts.

The writer downloaded firmware for the cameras from Hanwha’s website and took it apart using tools like binwalk and ghidra. At first, some files were locked, but with help from another blog, they found the password method—just the model number with a prefix. Inside, there was another layer of encryption, but the key and IV were hardcoded, meaning anyone with the software could get them. The author used these to unlock the main file system (rootfs).

After opening the files, they ran a tool called trufflehog and quickly found a GitHub admin token in about 30 files. This token gave admin access to many GitHub repositories. The reason for the leak was a bad build step: the whole environment, including secret tokens, was written into the camera’s UI files.

Some environment variables had US Department of Defense (DoD) IP addresses. The writer wondered if this was just a mistake or if Hanwha had closer ties to the DoD through its parent company or sister companies. To check if this was common, the author downloaded firmware for about 500 camera models. In 62% of them, they could use the same process to extract files, but only three had the same GitHub token inside.

The author sent a report to Hanwha, and the company quickly fixed the problem by revoking the token. The writer was happy with the fast response but worried that these mistakes keep happening.

Many Hacker News users were shocked that a security camera—something meant to protect—had such a basic security problem. Some said this shows companies still do not handle secrets carefully, even after years of warnings. Others pointed out that adding all environment variables to build files is a common but dangerous mistake. A few people mentioned that tools like trufflehog help catch these errors, but only if used before release.

Some commenters discussed the risks of using hardcoded keys, saying it makes all cameras easy targets once the secret is out. There were jokes about the irony: cameras made for security actually weaken it. A few users wondered about the DoD addresses, guessing they were just placeholder IPs, but some worried about possible government connections.

Others praised the author for responsible disclosure and Hanwha for acting fast. Some thought more companies should have easy ways to report security issues. A few users shared similar stories from other hardware, warning this is a wider problem. Finally, many agreed that companies must do better with secrets, especially when their products are in people’s homes and offices.

- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49026933)

This talk is about Fil-C, a new way to make C and C++ memory safe, shown by Filip Pizlo at SSW 2026. In the video, Filip says that normal C and C++ are not safe with memory, which can lead to bugs and attacks, and that is why many people want to move to other languages like Rust.

Fil-C is different. It is a new compiler and runtime for C and C++ that adds protections so memory bugs cannot be used to take over programs. Filip shows big live demos: first, he runs LibreOffice compiled with Fil-C, then he shows all its dependencies, and even a whole Linux distro compiled this way. He codes live to answer a question from the audience, making it clear Fil-C can handle real, complex programs. The main idea is Fil-C adds memory safety checks at runtime. All memory allocations are zero-initialized, so there is no uninitialized data. If you make a bug that would usually crash or allow an attack, Fil-C stops it safely or cleans up, so you cannot get remote code execution. Some people joke that Fil-C is like a really fast version of Valgrind (a tool for finding memory bugs), but it works all the time, not just in tests. There is a garbage collector, which makes memory management safer, more like Python, so you do not need to free memory by hand. The goal is to let people keep using C and C++ but with safety like modern languages.

People in the comments are very impressed by the live demos, especially compiling huge programs and a Linux system. Some say Filip’s skills are amazing. Others make jokes: one compares Fil-C and Rust to cars—Rust has good brakes, so you never crash; Fil-C has strong airbags, so you survive crashes. Some ask about performance, saying Fil-C is slower because of all the checks, and wonder if that is OK for real software. A few think Fil-C is best for testing and hardening, but maybe not for release builds, because of the overhead. Some like the idea of safer C, but want to know how hard it is to port Fil-C to BSD or other platforms. A few people wish for a version for Rust, or think it could help with memory safety drama between Zig and Rust users. One person asks how Fil-C compares to hardware solutions like ARM’s trusted firmware. There are also worries about every allocation being zeroed, which could be slow for some cases. - HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=49004464)

Marimo, which is a reactive notebook tool, now works inside PyCharm, a popular Python IDE. The marimo team released a plugin for PyCharm, so you can add marimo notebooks to your Python projects and use them without leaving the IDE.

With this plugin, you can create or open marimo notebooks right in PyCharm. These notebooks are just normal `.py` files with a special import and an App declaration, so they work well with git and other version control tools. When you update your Python code, marimo’s module reloader updates your notebook cells automatically, giving you quick feedback. You can switch between the interactive notebook view and the normal code editor easily.

The plugin manages marimo’s server, so you don’t need to run extra terminals or browser tabs. Notebooks run in your project’s chosen Python environment, so all your project’s dependencies are available. If marimo isn’t installed, the plugin can install it for you. There’s also a sandbox mode, where notebooks run in an isolated environment using a tool called `uv`; this keeps notebook dependencies separate from your main project.

You can use PyCharm’s usual tools, like database browsing, right next to your notebook, though database connections must be set up separately in marimo. The plugin also supports pairing your notebook with AI agents, such as Claude, Codex, or JetBrains’ own AI, so you can collaborate or get help from an AI inside PyCharm.

This plugin is open source and still new. The team wants feedback and bug reports to help improve it.

Others mention that live notebooks in IDEs can make testing and trying out code much easier. ## Designing an Ethernet Switch ASIC

- 原文链接: [Designing an Ethernet Switch ASIC](https://essenceia.github.io/projects/ethernet_switch_asic/)
- HN链接: [Hacker News讨论](https://news.ycombinator.com/item?id=48985182)

This article is about building an open source Ethernet switch ASIC, a custom chip for connecting network devices. The author is making a 3-port, unmanaged, 100 Mbps switch on a small, affordable silicon chip, hoping to get real, working chips back from the factory in November 2026.

Most open source hardware projects focus on CPUs, like RISC-V chips, but almost no one tries to make open source networking chips. Networking hardware is complicated and less exciting, so it gets less attention. Still, almost all open source routers today use closed, proprietary chips inside, so there is a big gap for open hardware in networking.

The author explains different types of switches: managed vs unmanaged, and cut-through vs store-and-forward. Managed switches can be configured, while unmanaged ones are plug-and-play. Cut-through switches forward packets faster but might send corrupted data; store-and-forward switches are safer but need more memory.

Because of the chip’s small size and limited pins, the design is for an unmanaged, cut-through switch. The chip uses 24 pins and works with cheap, common Ethernet PHY chips (like the LAN8720A) over an RMII interface. There’s not enough room for big memory, so store-and-forward is not possible.

The switch reads MAC addresses from incoming packets, keeps a small table (only 4 entries) to remember which device is on which port, and uses a time-to-live counter to forget old entries. If the table is full, it replaces the oldest entry. The author shares some stories about testing the design on an FPGA and running into slow network speed when using the prototype switch.

This chip is just the start—there are plans for more open source networking chips (all named after coffee). In the future, with a bigger chip and more pins, the author hopes to make an 8-port switch and use better memory (like CAM) for faster lookups.

In the Hacker News comments, many people are excited to see open source hardware moving into networking. Several users talk about how hard it is to make and test ASICs, and they praise the author’s detailed write-up and honesty about problems. Some comment that open source CPUs get more attention because they are easier to test in software and more people need them. Others point out that networking ASICs are usually very complex and controlled by a few big companies, so this project is very ambitious.

A few users ask technical questions about timing, memory limits, and whether the switch could ever support faster speeds or more ports. Some are curious about real-world use: could this ever be part of a home lab, or is it just for learning? Others share stories about their own FPGA or ASIC projects, saying it’s easy to run into “not enough pins” problems like the author did.

Some readers suggest that, even if this chip is simple, it’s a good starting point for teaching and for building a full open source router in the future. There are questions about open source toolchains and how hard it is to get chips manufactured, with answers explaining that shuttle runs like Tiny Tapeout help keep costs low. Overall, the comments show support, offer advice, and encourage the author to keep going with more open networking hardware.
